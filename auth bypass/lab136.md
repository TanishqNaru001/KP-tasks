# ControlHub - JSON Response Manipulation Auth Bypass

## Vulnerability Type
Broken Authentication / Client-Side Trust of Server Response (OWASP A07:2021 - Identification and Authentication Failures)

## Summary
The login mechanism on ControlHub relies on the client trusting the JSON response body returned by the server to determine authentication status and user role, instead of enforcing session/role state server-side. By intercepting the login response for a failed login attempt (wrong password) and modifying the `status` and `user_type` fields to indicate success and admin privileges, an attacker can bypass authentication entirely and gain admin-level access without valid credentials.

## Vulnerable Endpoint
`POST https://hackarena.site/subdomains/hub` (login)

## Steps to Reproduce
1. Go to the ControlHub login page.
2. Turn on intercept in Burp Suite (or similar proxy).
3. Submit the login form using a valid username and an **incorrect** password.
4. Intercept the server's response to this failed login attempt.
5. Modify the response body fields to reflect a successful, privileged login:
   - Change `"status"` to `"1"` (success)
   - Change `"user_type"` to `"admin"`
6. Forward the modified response to the client.
7. Observe that the application treats the session as authenticated with admin privileges, despite the password never being validated correctly server-side.

## Payload Used
Modified response forwarded in place of the failed-login response:
```json
{
    "status": "1",
    "user_type": "admin"
}
```

## Impact
- Complete authentication bypass — valid credentials are not required to gain access.
- Privilege escalation to admin-level access by directly setting `user_type` in the intercepted response.
- Confirms the application determines both login success and user role from client-visible response data rather than a server-enforced session/token, making account takeover and full administrative compromise trivial for anyone capable of intercepting traffic.

## Recommendations for Fix
- Authentication and authorization decisions must be made and enforced entirely server-side (e.g., via a signed session token or server-stored session state) - never inferred from a response body the client can modify.
- Issue a cryptographically signed token (e.g., JWT with server-side signature verification, or an opaque session ID mapped server-side) upon successful login, and validate it on every subsequent request.
- Role/privilege (`user_type`) must be looked up from the server-side session/database on each request, never trusted from a value returned in a prior response.
- Implement proper password verification with account lockout/rate-limiting on repeated failed attempts.
