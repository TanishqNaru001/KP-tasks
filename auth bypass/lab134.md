# OTP Verification Bypass via Response Manipulation

## Vulnerability Type
Broken Authentication / Improper Server-Side Session Validation (OWASP A07:2021 - Identification and Authentication Failures)

## Summary
The OTP verification mechanism on the signup flow relies on the client trusting the API response body to determine verification status, instead of enforcing a server-side session/state check. By intercepting the verification request and swapping a "failed" OTP response with a previously captured "success" response, an attacker can bypass OTP verification entirely and register an account without ever possessing a valid OTP (email/phone not actually verified).

## Vulnerable Endpoint
`POST https://hackarena.site/subdomains/verify/`

## Steps to Reproduce
1. Go to the signup page and fill in all required details (name, email, phone, etc.).
2. Turn on intercept in Burp Suite (or similar proxy).
3. Submit the signup form to trigger OTP generation.
4. Enter the **correct** OTP, intercept the response, and save it as the baseline "success" response.
   - Example: `{"status":"success","verified":true}`
5. Log out. Create a new signup with different details.
6. At the OTP step, intentionally enter a **wrong** OTP.
7. Intercept the response for this wrong-OTP attempt (typically a "failure" response).
   - Example: `{"status":"failed","verified":false}`
8. Replace the failure response body with the success response saved in step 4, then forward it to the client.
9. Observe that the application proceeds as if verification succeeded, despite the OTP never being validated correctly server-side.

## Payload Used
Captured success response, replayed over the failed-attempt response:
```json
{"status":"success","verified":true}
```

## Impact
- OTP verification can be bypassed without knowledge of the correct OTP.
- Attackers can create verified accounts using emails/phone numbers they do not own, since server-side state isn't enforced before marking a session as verified.
- Enables fake account creation, identity spoofing, and downstream abuse of any feature gated behind "verified" status.

## Recommendations for Fix
- Track verification state server-side (session or DB flag) immediately upon OTP validation - never derive it solely from the response body shown to the client.
- Re-validate verification status server-side on every protected/follow-up endpoint rather than trusting a client-supplied or client-visible flag.
- Invalidate the OTP after a single use and enforce rate-limiting/attempt caps to prevent brute-force guessing in parallel with this issue.
- Ensure OTP comparison logic happens entirely server-side with no client-controllable success/failure branching.
