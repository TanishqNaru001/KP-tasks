# Phone OTP Bypass via Response Manipulation

## Vulnerability Type
Broken Authentication / Improper Server-Side Session Validation (OWASP A07:2021 – Identification and Authentication Failures)

## Summary
The phone OTP verification mechanism relies on the client trusting the API response body to determine verification status, instead of enforcing a server-side session/state check. By intercepting the verification request and swapping a "failed" OTP response with a previously captured "success" response, an attacker can bypass phone verification entirely and register an account without ever possessing a valid phone number OTP.

## Vulnerable Endpoint
`POST https://hackarena.site/subdomains/mobile/`

## Steps to Reproduce
1. Go to the signup/verification page and enter full name and phone number.
2. Turn on intercept in Burp Suite (or similar proxy).
3. Submit the form to trigger OTP generation to the phone number.
4. Enter the **correct** OTP, intercept the response, and save it as the baseline "success" response.
   - Example: `{"status":"success","verified":true}`
5. Log out. Start a new flow with a different full name and phone number.
6. At the OTP step, intentionally enter a **wrong** OTP.
7. Intercept the response for this wrong-OTP attempt (typically a "failure" response).
   - Example: `{"status":"failed","verified":false}`
8. Replace the failure response body with the success response saved in step 4, then forward it to the client.
9. Observe that the application proceeds as if phone verification succeeded, despite the OTP never being validated correctly server-side.

## Payload Used
Captured success response, replayed over the failed-attempt response:
```json
{"status":"success","verified":true}
```

## Impact
- Phone OTP verification can be bypassed without knowledge of the correct OTP.
- Attackers can create verified accounts using phone numbers they do not own, since server-side state isn't enforced before marking a session as verified.
- Enables fake account creation, identity spoofing, and downstream abuse of any feature gated behind "phone verified" status.

## Recommendations for Fix
- Track verification state server-side (session or DB flag) immediately upon OTP validation - never derive it solely from the response body shown to the client.
- Re-validate verification status server-side on every protected/follow-up endpoint rather than trusting a client-supplied or client-visible flag.
- Invalidate the OTP after a single use and enforce rate-limiting/attempt caps to prevent brute-force guessing in parallel with this issue.
- Ensure OTP comparison logic happens entirely server-side with no client-controllable success/failure branching.
