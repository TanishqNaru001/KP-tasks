# Bug Report: Race Condition in OTP Resend Limit (Rate-Limit Bypass)

**Program / Target:** CodeShack
**Affected URL:** https://hackarena.site/subdomains/counter/register.php
**Affected Feature:** Email OTP verification after registration (resend OTP)
**Vulnerability Type:** Race Condition (TOCTOU), Improper Rate Limiting (CWE-362, CWE-799)
**Severity:** Medium (CVSS estimate: 5.3 to 6.5, depending on program impact rules)
**Reporter:** Tanishq
**Date Reported:** [DATE]

---

## Summary

The OTP resend function on the verification page advertises a limit of 3 resend attempts. The limit is enforced with a check-then-act pattern that is not atomic. When multiple resend requests are sent concurrently, the server processes them in parallel before the attempt counter is updated, so all of them pass the check. As a result, far more than 3 OTP emails can be generated and delivered to the user's inbox, and the intended resend limit is bypassed.

## Impact

- The resend limit provides no real protection. An attacker can trigger an unlimited number of OTP emails for an account in a single burst.
- Email flooding / mail bombing of a victim's inbox using the platform as the sending source.
- Abuse of the email service (cost and reputation impact on the sending domain).
- Increased risk to OTP-based verification if multiple valid OTPs remain active at the same time, since each resend may issue a new valid code.

## Steps to Reproduce

1. Open https://hackarena.site/subdomains/counter/register.php and register a new account using a test email address that you control.
2. After submitting, you are redirected to the OTP verification page.
3. Click the "Resend OTP" button once while intercepting traffic with a proxy (e.g., Burp Suite) and capture the resend request.
4. Send the captured request to Repeater and duplicate it 20 times. Group the requests together in a single tab group.
5. Use the Single-packet attack (HTTP/2) option to send all grouped requests simultaneously.
6. Check the test email inbox.

## Expected Result

The server should allow only 3 resend attempts in total. Any additional requests should be rejected, for example with HTTP 429 or an error message stating the limit was reached.

## Actual Result

All or most of the 20 concurrent requests were accepted. The test inbox received approximately 10 new OTP emails, well above the stated limit of 3.

## Root Cause (Suspected)

The resend counter is read, compared against the limit, and then updated in separate, non-atomic steps. Concurrent requests read the same counter value before any of them write the increment, so all of them pass the check. The OTP generation and email dispatch then run for each request.

## Recommended Remediation

1. Make the resend counter update atomic. Use a single database operation such as `UPDATE ... SET resend_count = resend_count + 1 WHERE user_id = ? AND resend_count < 3` and check the affected row count before sending an OTP.
2. Apply a database row lock (e.g., `SELECT ... FOR UPDATE`) or a server-side mutex keyed on the user or session while the resend is processed.
3. Enforce a cooldown between resends (e.g., 60 seconds) server-side, not only in the client-side UI.
4. Invalidate previously issued OTPs whenever a new one is generated, so only the latest code is valid.
5. Add per-account and per-IP rate limiting at the gateway or application layer for the OTP endpoints.
6. Log and alert on repeated resend requests for the same account.
