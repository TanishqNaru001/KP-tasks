# Bug Report: Race Condition in Survey Credit Claim (Unlimited Credits)

**Program / Target:** Slack (as listed in the report title; target host is hackarena.site)
**Affected URL:** https://hackarena.site/subdomains/race_condition/signup.php
**Affected Feature:** Workspace creation flow, post-signup survey credit claim ($100 credit)
**Vulnerability Type:** Race Condition (TOCTOU), Business Logic Flaw (CWE-362, CWE-840)
**Severity:** High (CVSS estimate: 7.1 to 8.1, depending on program impact rules and the monetary value of credits)
**Reporter:** Tanishq
**Date Reported:** [DATE]

---

## Summary

After creating a workspace, users are asked to complete a survey to claim a $100 credit. The server checks whether the credit has already been claimed and then grants it, but these steps are not atomic. When several survey submissions are sent concurrently, the server processes them in parallel before the "already claimed" state is written, so every request passes the check and grants the credit. In testing, a single page refresh after the attack showed $1,000 in credits, which is ten times the intended single $100 reward.

## Impact

- A user can accumulate credits far beyond the single $100 reward the survey is meant to grant.
- Direct financial loss to the company, since credits represent monetary value.
- Abuse at scale: the same technique can be scripted across many accounts.
- Undermines trust in the promotional and billing system.

## Steps to Reproduce

1. Open https://hackarena.site/subdomains/race_condition/signup.php.
2. Fill in all required details and click "Create Workspace".
3. On the next page, open the survey used to claim the $100 credit.
4. While intercepting traffic with a proxy (e.g., Burp Suite), fill in the survey and submit it. Capture the survey submission request.
5. Send the captured request to Repeater and create a group of duplicate requests.
6. Use the Single-packet attack (HTTP/2) option to send all grouped requests simultaneously.
7. Refresh the page or check the credit or billing balance.

## Expected Result

The $100 survey credit should be granted once per workspace or account. Any further submissions should be rejected, for example with an "already claimed" message.

## Actual Result

Multiple survey submissions were accepted in the same burst. After refreshing the page, the balance showed $1,000 in credits instead of $100.

## Root Cause (Suspected)

The "credit already claimed" check and the credit grant are separate, non-atomic operations. Concurrent requests read the flag before any of them sets it, so each one passes the check and grants the credit.

## Recommended Remediation

1. Make the claim atomic. Use a conditional database update such as `UPDATE credits SET claimed = 1 WHERE account_id = ? AND claimed = 0` and grant the credit only if the affected row count is 1.
2. Add a unique constraint on (account_id, promotion_id) for credit grants, so duplicate grants are rejected at the database level.
3. Use a database transaction with a row lock (e.g., `SELECT ... FOR UPDATE`) around the check and grant.
4. Rate-limit or deduplicate survey submissions per account.
5. Audit existing accounts for credits granted above the intended amount and reverse any unauthorized grants.
