# Bug Report: Race Condition in Team Member Invitations (Invite Limit Bypass)

**Program / Target:** Omise (as listed in the report title; target host is hackarena.site)
**Affected URL:** https://hackarena.site/subdomains/condition/register.php
**Affected Feature:** Dashboard, "Invite Member" function
**Vulnerability Type:** Race Condition (TOCTOU), Improper Rate Limiting (CWE-362, CWE-799)
**Severity:** Medium (CVSS estimate: 5.3 to 6.5, depending on program impact rules)
**Reporter:** Tanishq
**Date Reported:** [DATE]

---

## Summary

The dashboard's "Invite Member" function appears to enforce a limit on invitations, but the check and the send operation are not atomic. When several invite requests are sent concurrently, the server processes them in parallel before the invitation count is updated, so each request passes the check. Multiple invitation emails were delivered to the target address from a single burst of requests, bypassing the intended limit.

## Impact

- The invitation limit provides no real protection against abuse.
- Email flooding of arbitrary addresses using the platform as the sender.
- Abuse of the email service, with cost and sender reputation impact.
- Potential for invitation-based account or seat abuse, where more members are added than the plan allows.

## Steps to Reproduce

1. Open https://hackarena.site/subdomains/condition/register.php and register a new account using a test email address that you control.
2. After registration, you are taken to the dashboard.
3. Navigate to the "Invite Member" function.
4. While intercepting traffic with a proxy (e.g., Burp Suite), submit one invitation and capture the request.
5. Send the captured request to Repeater and create a group of duplicate requests.
6. Use the Single-packet attack (HTTP/2) option to send all grouped requests simultaneously.
7. Check the test email inbox.

## Expected Result

The server should send invitations only up to the defined limit. Additional requests should be rejected, for example with HTTP 429 or a message stating the limit was reached.

## Actual Result

Multiple requests were accepted in the same burst, and multiple invitation emails were received in the test inbox.

## Root Cause (Suspected)

The invitation count is read, compared against the limit, and then updated in separate, non-atomic steps. Concurrent requests read the same count before any of them write the increment, so all of them pass the check and send an email.

## Recommended Remediation

1. Make the invitation counter update atomic, for example `UPDATE accounts SET invites_sent = invites_sent + 1 WHERE id = ? AND invites_sent < ?` and send the email only if the affected row count is 1.
2. Use a database transaction with a row lock (e.g., `SELECT ... FOR UPDATE`) around the check and send step.
3. Enforce per-account and per-IP rate limits on the invite endpoint at the gateway or application layer.
4. Deduplicate invitations to the same email address within a short time window.
5. Add a unique constraint on pending invitations per (account_id, invitee_email).
6. Log and alert on bursts of invitation requests from a single account.
