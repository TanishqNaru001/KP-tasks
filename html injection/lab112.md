## Title
Stored HTML Tag Injection via Username and Full Name Fields - GitLab Clone Code Platform

## Vulnerability Type
Stored HTML Injection

## Severity
Medium

## Summary
The GitLab clone at `https://hackarena.site/subdomains/code/` stores user-supplied input in the Username and Full Name fields (via the Settings page) without sanitization or output encoding. The injected HTML persists in the database and executes when the attacker's username is rendered on the Snippets page — visible to any user who visits that page. This is a stored vulnerability, meaning no victim interaction beyond normal browsing is required for the injection to affect them.

## Vulnerable Endpoint
**Injection point:** `https://hackarena.site/subdomains/code/index.php?view=settings`

**Trigger / execution point:** `https://hackarena.site/subdomains/code/index.php?view=snippets`

## Vulnerable Fields
| Field | Trigger Location |
|---|---|
| Username | Snippets page - where username is displayed alongside snippets |
| Full Name | Snippets page - where full name is displayed |

## Steps to Reproduce

### Step 1 - Inject payload via Settings
1. Log in to the platform and navigate to:
   `https://hackarena.site/subdomains/code/index.php?view=settings`
2. In the **Username** field, enter:
   ```html
   <h1 style="color:red">HACKED</h1>
   ```
3. In the **Full Name** field, enter:
   ```html
   <h1 style="color:red">HACKED</h1>
   ```
4. Save the settings.

### Step 2 - Trigger payload via Snippets page
1. Navigate to:
   `https://hackarena.site/subdomains/code/index.php?view=snippets`
2. Observe that the injected HTML renders in the page — the username/full name appears as a styled heading rather than plain text, confirming stored HTML injection.

## Impact
Stored HTML Injection in a code-sharing platform carries meaningful real-world risk:

- **Any user who visits the Snippets page** sees the injected HTML rendered in their browser — no crafted link required.
- **Page defacement** - an attacker can inject misleading content, fake error messages, or offensive text that appears to originate from the platform.
- **Phishing via injected links** - injecting `<a href="https://evil.com">Login here</a>` in a username field causes a convincing fake link to appear next to every snippet the attacker posts, targeting other developers on the platform.
- **Fake UI overlays** - injecting styled forms or banners mimicking the platform's design can trick users into submitting credentials or sensitive data.
- **Escalation path to XSS** - if the HTML filter is incomplete, event-handler payloads (`<img onerror=confirm(1)>`) or script tags may execute — worth testing in the same fields.

## Recommendations for Fix
1. Apply context-aware output encoding on Username and Full Name fields before rendering them anywhere (e.g. `htmlspecialchars($username, ENT_QUOTES, 'UTF-8')` in PHP) — this converts `<`, `>`, and `"` into harmless HTML entities.
2. Enforce input validation at the settings save endpoint - usernames should only accept alphanumeric characters, hyphens, underscores, and dots. Reject any input containing `<` or `>` outright.
3. Audit every page that renders the username or full name (profile, snippets, comments, activity feed, merge requests) and ensure the same encoding is applied consistently across all display contexts.
4. Add a Content-Security-Policy header as defense-in-depth to limit damage if encoding is missed on any rendering path.
