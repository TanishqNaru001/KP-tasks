## Title
HTML Injection in Email Notification via First Name and Last Name Fields - Community Application Form

## Vulnerability Type
HTML Injection (Email Context)

## Severity
Medium

## Summary
The community application form at `https://hackarena.site/subdomains/notifications/` reflects the First Name and Last Name fields directly into an automated notification email without sanitization or output encoding. When an applicant submits the form with HTML payloads in their name fields, the injected markup renders as real HTML in the notification email received by the applicant (and potentially by platform staff reviewing the application). This allows an attacker to manipulate the content, layout, and links of an official platform email —- making it an effective phishing and brand abuse vector.

## Vulnerable Endpoint
**Injection point (form):** `https://hackarena.site/subdomains/notifications/`

**Post-submission redirect:** `https://hackarena.site/subdomains/notifications/index.php`

**Execution context:** Notification email sent to the address provided during application

## Vulnerable Fields
| Field | Execution Context |
|---|---|
| First Name | Rendered in notification email body |
| Last Name | Rendered in notification email body |

## Steps to Reproduce

### Step 1 - Fill application form with payload
1. Navigate to `https://hackarena.site/subdomains/notifications/`
2. Fill the community application form with the following:
   - **First Name:**
     ```html
     <h1 style="color:red">HACKED</h1>
     ```
   - **Last Name:**
     ```html
     <a href="https://evil.com">Click to verify your account</a>
     ```
   - **Email:** Use your own email address to receive the notification.
3. Submit the form.

### Step 2 - Observe redirect
1. After submission, observe redirect to:
   `https://hackarena.site/subdomains/notifications/index.php`

### Step 3 - Open notification email
1. Open the notification email received at the address entered during the application.
2. Observe that the injected HTML renders in the email body - the First Name appears as a styled red heading and the Last Name appears as a real, clickable hyperlink — confirming HTML injection in the email template.

## Payload Used
```html
First Name:  <h1 style="color:red">HACKED</h1>
Last Name:   <a href="https://evil.com">Click to verify your account</a>
```

## Impact
HTML Injection in an email context is more impactful than the same injection on a web page for several reasons:

- **Email is inherently trusted** - a notification email arriving from an official platform domain (`hackarena.site`) carries far more trust than a crafted URL. Victims are significantly more likely to click injected links inside official-looking emails.
- **Phishing via official email sender** - an attacker can inject a convincing "Verify your account" or "Reset your password" link pointing to an attacker-controlled domain, sent via the platform's own email infrastructure. This is a near-perfect phishing vector.
- **Email client HTML rendering** - most modern email clients (Gmail, Outlook, Apple Mail) render HTML in emails, meaning injected styles, images, forms, and links all display as intended by the attacker.
- **Brand abuse** - the injected content appears to come from the platform itself (sent from the platform's email, with the platform's headers), making the attack extremely difficult for a recipient to distinguish from a legitimate email.
- **Staff/admin targeting** - if the same notification email is also sent to platform staff reviewing the application, injected content renders in their inbox too — a step toward phishing staff credentials via official email channels.
- **No victim interaction on a website required** - the attack surface is the victim's email inbox, not a URL they must click. Simply opening the email is sufficient.

## Recommendations for Fix
1. Sanitize and output-encode all user-supplied fields before inserting them into email templates. In PHP, apply `htmlspecialchars($value, ENT_QUOTES, 'UTF-8')` to First Name, Last Name, and all other form fields before placing them in the email body - this converts `<`, `>`, and `"` into HTML entities that render as plain text.
2. Treat user-supplied name fields as plain text only - never allow them to contain or render HTML. Validate at submission time: reject inputs containing `<`, `>`, or `"` in name fields.
3. Use a templating engine that auto-escapes variables by default (e.g. Twig, Blade, Mustache) rather than manually concatenating user input into email HTML - auto-escaping engines prevent this class of injection by design.
4. Audit all other form fields (company name, message body, subject) that feed into email templates for the same issue.
