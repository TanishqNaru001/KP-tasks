# Time-Based Blind SQL Injection in Orders Search `name_to_find` Parameter

## Vulnerability Type
SQL Injection (Blind, Time-Based) - CWE-89

## Summary
The `name_to_find` GET parameter on the orders/places search functionality is not sanitized before being used in a backend SQL query. Injecting conditional SQL logic via this parameter causes a measurable response delay, confirming the input is concatenated directly into the query without parameterization. Given this is on an "orders" subdomain, the underlying query likely touches order/transaction records, making this a viable vector for extracting potentially sensitive business or customer data.

## Vulnerable Endpoint
```
GET https://kzlabs.in/subdomains/orders/index.php?name_to_find=
```

## Steps to Reproduce
1. Intercept the orders search request in Burp Suite (or browse directly with the payload in the URL).
2. Mark the `name_to_find` parameter as the injection point.
3. Submit the payload below as the search value.
4. Observe a ~10 second response delay compared to the baseline (sub-second) response for a normal search term.
5. Re-send to confirm the delay is consistent and reproducible.
6. (Recommended follow-up) Check whether this query touches order/payment-related tables, which would raise the sensitivity of exposed data if extraction is attempted.

## Request
```
GET /subdomains/orders/index.php?name_to_find=1'XOR(94102*if(now()=sysdate(),sleep(10),0))XOR'Z HTTP/2
Host: kzlabs.in
```

## Payload Used
```
1'XOR(94102*if(now()=sysdate(),sleep(10),0))XOR'Z
```

URL-encoded form (as sent):
```
1%27XOR%2894102*if%28now%28%29%3Dsysdate%28%29%2Csleep%2810%29%2C0%29%29XOR%27Z
```

## Impact
- **Confidentiality:** Blind extraction of database contents via time-based inference - potentially exposing order records, customer names, or transaction details depending on what this search queries against.
- **Severity:** High - unauthenticated access point, no login required, no user interaction needed from a victim.

## Recommendations for Fix
1. **Parameterized queries/prepared statements** for the `name_to_find` lookup query - never concatenate raw user input into SQL.
2. **Input validation** on the search parameter - enforce expected character sets and length limits.
3. **Least-privilege DB account** so the web app's DB user cannot access data beyond what this search feature requires.
4. **WAF rule** to block SQLi patterns on this endpoint as an interim mitigation while the code fix is deployed.
5. **Note the recurring pattern:** this is the sixth endpoint on this application found vulnerable to the identical injection style, strongly suggesting a single shared, unsanitized query-building function reused across subdomains rather than independent bugs — recommend a codebase-wide audit rather than point fixes per endpoint.
