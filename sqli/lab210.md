# Time-Based Blind SQL Injection via User-Agent Header (Stats/Analytics Logging)

## Vulnerability Type
SQL Injection (Blind, Time-Based, HTTP Header-based) - CWE-89

## Summary
The `User-Agent` HTTP header is not sanitized before being used in a backend SQL query on the stats subdomain, likely as part of request/visitor logging logic that runs independently of the contact form's own submission handling. Injecting conditional SQL logic via the `User-Agent` header causes a measurable response delay, confirming the header value is concatenated directly into a SQL statement without parameterization. This is a notable finding because it is not tied to a visible input field — any request to this endpoint (including automated bot/crawler traffic) could trigger the vulnerable code path, and because the header is likely logged, it may also pose a second-order/stored injection risk if the logged value is later queried or displayed (e.g., in an analytics dashboard).

## Vulnerable Endpoint
```
POST https://kzlabs.in/subdomains/stats/index.php
```

## Steps to Reproduce
1. Submit the contact form on `/subdomains/stats/` normally and observe that no visible response/behavior change occurs - indicating server-side processing may be happening silently (e.g., logging) rather than in the visible form response.
2. Intercept the POST request in Burp Suite.
3. Replace the `User-Agent` header value with the payload below, leaving form fields (`full_name`, `email`, etc.) as normal values.
4. Send the request and observe a ~10 second response delay compared to the baseline (sub-second) response with a normal User-Agent string.
5. Re-send to confirm the delay is consistent and reproducible.
6. (Recommended follow-up) Check whether an admin/analytics panel exists that displays logged User-Agent strings - if so, test for second-order SQLi or stored XSS there as well, since raw header values appear to be persisted and/or processed server-side.

## Request
```
POST /subdomains/stats/index.php HTTP/2
Host: kzlabs.in
Cookie: PHPSESSID=eku7qbgh4ve6ugik6eftsbautj

```

## Impact
- **Confidentiality:** Blind extraction of database contents via time-based inference - scope depends on what the stats/logging query touches (visitor logs, possibly linked to contact submissions).
- **Attack surface breadth:** Since this is header-based rather than form-field-based, it is exploitable by any client reaching this endpoint, including automated scanners/bots, and does not require interacting with the visible form at all.
- **Stored/second-order risk:** If the User-Agent is logged and later rendered or queried in an admin/analytics view, this could escalate to stored SQLi or stored XSS.
- **Severity:** High - unauthenticated, no user interaction required, broad exploitability via header injection.

## Recommendations for Fix
1. **Parameterized queries/prepared statements** for any logging or analytics query that incorporates request headers, including `User-Agent`.
2. **Treat all HTTP headers as untrusted input** - never log or query header values without sanitization, since headers are fully attacker-controlled.
3. **Output encoding** wherever logged User-Agent strings are later displayed (e.g., analytics dashboard) to prevent second-order injection/XSS.
4. **Least-privilege DB account** so the web app's DB user cannot access data beyond what logging requires.
5. **WAF rule** to block SQLi patterns in HTTP headers as an interim mitigation while the code fix is deployed.
6. **Codebase-wide audit recommended:** this is the seventh endpoint found vulnerable to the identical injection pattern (including now a non-form, header-based vector), strongly indicating a shared, unsanitized query-building utility used throughout the application rather than isolated per-endpoint bugs.
