# Time-Based Blind SQL Injection in Comment Posting Feature (INSERT Context)

## Vulnerability Type
SQL Injection (Blind, Time-Based, INSERT context) - CWE-89

## Summary
The `comment` POST parameter on the reviews/comment system is not sanitized before being used in a backend SQL `INSERT` statement. Injecting conditional SQL logic via the `comment` field causes a measurable response delay, confirming the input is concatenated directly into the query without parameterization. Unlike the login/search injection points, this is in an **INSERT context**, meaning an attacker could potentially also leverage stacked queries (if supported by the driver/DB config) or use this as a second-order injection vector if stored comments are later read back into another unsanitized query elsewhere in the app (e.g., an admin comment-review panel).

## Vulnerable Endpoint
```
POST https://kzlabs.in/subdomains/reviews/index.php
```

## Steps to Reproduce
1. Intercept the comment submission POST request in Burp Suite.
2. Send to Repeater/Intruder, marking the `comment` parameter as the injection point.
3. Submit the payload below as the comment body.
4. Observe a ~10 second response delay compared to the baseline (sub-second) response for a normal comment submission.
5. Re-send to confirm the delay is consistent and reproducible.
6. (Recommended follow-up) Check the admin/moderation panel (if accessible) to see whether the raw comment is later rendered or queried elsewhere, which would indicate a second-order injection risk in addition to the direct one.

## Request
```
POST /subdomains/reviews/index.php HTTP/2
Host: kzlabs.in
Cookie: PHPSESSID=eku7qbgh4ve6ugik6eftsbautj
Content-Type: application/x-www-form-urlencoded

action=post_comment&comment=qw1'XOR(94102*if(now()=sysdate(),sleep(10),0))XOR'Zer
```

## Impact
- **Confidentiality:** Blind data extraction via time-based inference, same as other injection points on this app.
- **Integrity:** Since this is an INSERT, a malicious comment could corrupt stored data or, if stacked queries are possible, modify other table data.
- **Stored/Second-order risk:** If comments are later processed in an admin panel or another query without sanitization, this could escalate to a stored SQLi or even stored XSS depending on how comments are rendered.
- **Severity:** High - unauthenticated (or low-privilege) submission point, no user interaction required from a victim, persistent storage increases blast radius.

## Recommendations for Fix
1. **Parameterized queries/prepared statements** for the comment INSERT statement - never concatenate raw user input into SQL.
2. **Input validation and length limits** on the `comment` field to reduce injectable surface.
3. **Output encoding** wherever comments are rendered (admin panel, public page) to prevent any secondary injection/XSS from already-stored malicious input.
4. **Least-privilege DB account** so the web app's DB user cannot perform destructive operations beyond what the comment feature needs.
5. **WAF rule** to block SQLi patterns on this endpoint as an interim mitigation while the code fix is deployed.
