# Time-Based Blind SQL Injection via Referer Header (Affiliate Tracking)

## Vulnerability Type
SQL Injection (Blind, Time-Based, HTTP Header-based) - CWE-89

## Summary
The `Referer` HTTP header is not sanitized before being used in a backend SQL query on the affiliate subdomain, most likely as part of referral/traffic-source tracking logic (common on affiliate pages, which log where visitors came from). Injecting conditional SQL logic via the `Referer` header causes a measurable response delay, confirming the header value is concatenated directly into a SQL statement without parameterization. Like the User-Agent-based finding on the stats subdomain, this is exploitable without touching any visible form or parameter — any GET request to this page with a crafted Referer header triggers the vulnerable code path, including from automated crawlers or bots that set custom Referer values.

## Vulnerable Endpoint
```
GET https://kzlabs.in/subdomains/affiliate/
```

## Steps to Reproduce
1. Intercept a GET request to `/subdomains/affiliate/` in Burp Suite.
2. Replace the `Referer` header value with the payload below.
3. Send the request and observe a ~10 second response delay compared to the baseline (sub-second) response with a normal/absent Referer header.
4. Re-send to confirm the delay is consistent and reproducible.
5. (Recommended follow-up) Check whether an affiliate/referral dashboard exists that displays logged Referer values — if so, test for second-order SQLi or stored XSS there as well.

## Request
```
GET /subdomains/affiliate/ HTTP/2
Host: kzlabs.in
Cookie: PHPSESSID=r8dph5268d9neutemcc1q42p9k
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/154.0.0.0 Safari/537.36
Referer: 1'XOR(94102*if(now()=sysdate(),sleep(10),0))XOR'Z
```

## Payload Used
```
1'XOR(94102*if(now()=sysdate(),sleep(10),0))XOR'Z
```

## Impact
- **Confidentiality:** Blind extraction of database contents via time-based inference - likely scoped to affiliate/referral tracking data, possibly linked to affiliate account or commission records.
- **Attack surface breadth:** Header-based and unauthenticated - exploitable by any client, including bots, without interacting with any visible page element.
- **Stored/second-order risk:** If the Referer value is logged and later rendered or queried in an affiliate dashboard, this could escalate to stored SQLi or stored XSS.
- **Severity:** High - unauthenticated, no user interaction required, broad exploitability via header injection.

## Recommendations for Fix
1. **Parameterized queries/prepared statements** for any referral-tracking query that incorporates the `Referer` header.
2. **Treat all HTTP headers as untrusted input** - never log or query header values (Referer, User-Agent, X-Forwarded-For, etc.) without sanitization.
3. **Output encoding** wherever logged Referer values are later displayed (e.g., affiliate dashboard) to prevent second-order injection/XSS.
4. **Least-privilege DB account** so the web app's DB user cannot access data beyond what tracking requires.
5. **WAF rule** to block SQLi patterns in HTTP headers as an interim mitigation while the code fix is deployed.
6. **Codebase-wide audit strongly recommended:** this is the eighth endpoint found vulnerable to the identical injection pattern across forms, GET parameters, and now two separate HTTP headers — this is conclusive evidence of a single shared, unsanitized query-building utility used application-wide, not isolated per-endpoint bugs. A point-by-point fix approach will likely miss additional instances; a full source review of the query-building layer is warranted.
